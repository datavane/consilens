# 本地文件基准

`bin/run-file-benchmark.sh` 运行 CSV/Parquet 端到端比对基准：生成文件、构建 `CompareRequest`，每次测量真实执行 `DefaultCompareRuntime`（文件连接器 + streaming merge），不是纯算法微基准。

## 一、运行

```bash
bin/run-file-benchmark.sh
```

脚本会先打包 benchmark 模块，再构建完整 classpath，直接启动 JMH（forked VM 需要完整 `java.class.path`，`exec:java` 无法传递）。

参数：

- 行数：10,000 / 100,000
- 格式：CSV / Parquet
- 差异比例：0%/5%（5% 时每 20 行改一行 `payload`）
- JMH：1 fork、1 warmup、1 measurement（快速冒烟，不是严格统计）

## 二、输出

```text
benchmark,rows,format,diffRatio,score,unit
FileDiffBenchmark,10000,csv,0.00,22.9294,ms/op
FileDiffBenchmark,100000,csv,0.00,310.8251,ms/op
FileDiffBenchmark,10000,parquet,0.00,48.8545,ms/op
FileDiffBenchmark,100000,parquet,0.00,337.5859,ms/op
...
```

## 三、参考结果

以下为 2026-10-27 在本机（Apple Silicon、JDK 11、单 fork/单轮测量）的结果，仅用于趋势参考：

| 行数 | 格式 | 差异比例 | 平均耗时 |
| ---: | --- | ---: | ---: |
| 10,000 | CSV | 0% | 22.9 ms |
| 100,000 | CSV | 0% | 310.8 ms |
| 10,000 | Parquet | 0% | 48.9 ms |
| 100,000 | Parquet | 0% | 337.6 ms |
| 10,000 | CSV | 5% | 22.6 ms |
| 100,000 | CSV | 5% | 264.4 ms |
| 10,000 | Parquet | 5% | 42.6 ms |
| 100,000 | Parquet | 5% | 307.9 ms |

说明：

- CSV 扫描时全量载入内存并按 key 排序；Parquet 经 DuckDB 读取后再排序。
- 结果受文件缓存、临时目录、JVM 预热影响较大；正式对比应增加 fork/iteration 并固定环境。
- 该基准同时接入 `BenchmarkSuite`（场景 `F01`/`F02`），可通过 `bin/run-benchmark.sh micro` 参与 baseline/drift；独立脚本保留用于快速跑单类基准。
- 正式对比应增加 fork/iteration 并固定环境。

## 四、规模外推（1e9 行决策门）

`devlop/scripts/spark-gate.sh` 用本机实测数据回答「单机能否跑 1e9 行」，同时给出时间与内存两个维度（脚本不启动容器）。

时间维度（Parquet、5% 差异、100k 行基准线性外推）：

| 引擎 | 实测 | 外推 1e9 行 | 8 小时预算 |
| --- | ---: | ---: | --- |
| Java（streaming 合并） | 270.7 ms / 100k 行 | ≈ 0.75 h | 通过 |
| Java（5M 行直测） | 13.8 s / 5M 行 | ≈ 46 min | 通过 |

内存维度（CSV 扫描，默认流式合并把两侧行读入堆内排序，峰值随行数近似线性）：

| 行数 | 最小可用堆 | 实测耗时 |
| ---: | ---: | ---: |
| 2,000,000 | `-Xmx2g`（`-Xmx1g` OOM） | 5.7 s |
| 5,000,000 | `-Xmx5g`（`-Xmx4g` OOM） | 13.8 s |

按 5M 行 / 5g 线性外推：64g 堆约可处理 6400 万行，128g 约 1.28 亿行，均远低于 1e9 行。

结论（2026-10-30）：

- **时间不是瓶颈，内存是**：单机 1e9 行的耗时在预算内，但当前文件扫描的内存模型撑不住；
- 1e9 行需要先落地 split-aware 扫描 + 外部排序（或用 DuckDB 引擎的溢写路径），再评估分布式后端；
- 因此 0.1 维持「单机 + 分区/窗口」范围，不立项 Spark；决策门脚本保留内存维度，避免只看耗时误判。

DuckDB 引擎（本地文件）参考值：5M 行 diff 2.7 s、峰值 RSS 2.3 GB，比默认引擎省内存，但同样随行数线性增长。

## 五、主套件中的场景

`bin/run-benchmark.sh micro` 现在同时运行算法基准与文件基准：

| 场景 | 含义 |
| --- | --- |
| `M01.<rows>.ratio<r>` | LocalDiffEngine 无差异 |
| `M02.<rows>.ratio<r>` | LocalDiffEngine 有差异 |
| `F01.<rows>.<format>.ratio<r>` | 文件端到端无差异 |
| `F02.<rows>.<format>.ratio<r>` | 文件端到端有差异 |

- `ms/op` 指标按 latency 处理：越低越好，micro 回归阈值 15%。
- 没有 baseline 时标记 NEW（WARN），不会让门禁失败。
- `BenchmarkSuite` 不再强制 JMH `Throughput` 模式，各 benchmark 使用自己的 `@BenchmarkMode`。

## 六、扩展

- 新增格式：在 `FileDiffBenchmark` 增加 `@Param` 与写入逻辑。
- 新增场景：调整 `rows`/`diffRatio`；保持 CSV 输出列不变，便于脚本聚合。
- 与 CI 集成时建议使用 `@Fork(3)`、更长 measurement，并记录 JDK/OS/磁盘信息。
