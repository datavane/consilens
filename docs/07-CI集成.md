# CI 集成

Consilens 的 CI 入口是独立的 `verify` 子命令：它执行一次比对，按策略判定通过/失败，并输出 JSON、JUnit、SARIF、Markdown 报告。`verify` 不负责调度、通知或历史存储，这些交给 CI 平台。

## 一、本地/流水线命令

```bash
consilens-cli.sh verify \
  -c examples/mysql-to-mysql.yaml \
  --fail-on new \
  --baseline .consilens/baseline.jsonl \
  --max-mismatch-rate 0.5 \
  --max-row-count-delta-pct 1.0 \
  --max-new-differences 0 \
  --required-columns id,amount \
  --format junit,markdown,sarif \
  --output-dir consilens-reports
```

| 选项 | 作用 |
| --- | --- |
| `--fail-on any` | 存在任何差异即失败（默认值） |
| `--fail-on new` | 只把基线中不存在的新差异视为失败，需要 `--baseline` |
| `--fail-on none` | 只生成报告，不因差异失败；策略项仍会记录 |
| `--max-mismatch-rate` | 变更行 / (sourceRows + targetRows) 的上限，取值 `0..1`（如 `0.5` 表示 50%） |
| `--max-row-count-delta-pct` | 两侧行数差异百分比上限 |
| `--max-new-differences` | 相对基线新增差异数量上限 |
| `--required-columns` | 必须出现在比较字段中的列；缺失即策略失败 |
| `--engine` | `java`（默认）或 `duckdb`（本地文件）；见 [DuckDB 行级比对](./18-DuckDB行级比对.md) |
| `--max-rows-scanned` | 扫描行数上限；**只对"行在本地过"的计划（join / java / streaming、以及 pushdown 里回退到本地比对的分段）生效**，纯 SQL 哈希对比不累计行数——设了它时 CLI 会打印 WARN |
| `--baseline` | 上一次运行产生的 JSONL diff-record 文件；由 `format: jsonl`、`type: diff-record` 的 sink 生成（见 [配置详解](./02-配置详解.md#jsonl-format)） |
| `--format` | `json`、`junit`、`sarif`、`markdown`，可逗号组合 |
| `--output-dir` | 报告目录，默认 `./consilens-report` |

退出码（**仅 `verify`**）：`0` 通过；`1` 差异/策略失败；`2` 执行或配置错误；`3` 无法判定（如策略不可评估）；`4` 预算超限。

> ⚠️ `diff --fail-on-diff` 的退出码**不属于**这张表：它在"发现差异"时返回 `2`，
> 而 `verify` 的 `2` 表示"执行或配置错误"。同一个数字在两处含义相反，CI 脚本若统一按这张表
> 判断，会把"有差异"误当成"基础设施故障"去重试/告警。门禁请用 `verify`（差异=1）；
> 保留 `diff --fail-on-diff` 只是为了兼容只关心"有没有差异"的旧脚本。

### `diff` 的退出码（与 `verify` 不同）

`diff` 只有三个码，且**与 `verify` 的码表不可互换**（实测）：

| 码 | 含义 |
| --- | --- |
| `0` | 比对执行完成。**注意：发现差异也是 0**——`diff` 默认不因差异失败 |
| `1` | 执行或配置错误（配置文件缺失、`--engine duckdb` 遇到非 `file` 源、键类型不一致等） |
| `2` | 仅当加了 `--fail-on-diff` 且确实发现差异时返回 |

三处同号异义要留意：

- `1`：`diff` 是"出错了"，`verify` 是"有差异/策略失败"；
- `2`：`diff --fail-on-diff` 是"有差异"，`verify` 是"执行或配置错误"；
- `0`：`diff` 不保证"一致"，只看"跑完了"。

所以 CI 门禁用 `verify`；只有"不关心差异内容、只想确认能跑通"的场景才用 `diff`。

### 生成基线

在配置的 `result.sinks` 中加入 JSONL sink，跑一次 `diff` 即可得到基线：

```yaml
result:
  sinks:
    - type: diff-record
      format: jsonl
      properties: '{"path":".consilens/baseline.jsonl"}'
```

基线身份是 `operation|primaryKey|sortedChangedColumns`，因此同一条记录的同一列再次变化不会被当成“新差异”，而列集合变化会被识别。

## 二、GitHub Action

仓库内置复合 Action：`.github/actions/consilens-verify`。

```yaml
- uses: actions/checkout@v4

- name: Consilens verify
  id: consilens
  uses: datavane/consilens/.github/actions/consilens-verify@v0.1.0
  with:
    config: consilens/compare.yaml
    version: 0.1.0          # 不填则要求 consilens-cli.sh 已在 PATH
    fail-on: new
    engine: java            # 本地文件可用 duckdb
    baseline: consilens/baseline.jsonl
    max-mismatch-rate: '0.5'
    format: junit,markdown
    output-dir: consilens-reports

- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: consilens-reports
    path: consilens-reports/
```

完整模板见 `.github/actions/consilens-verify/example-workflow.yml`。

Action 行为：

1. 设置 `version` 时从 GitHub Release 下载对应发行包并解压到 `RUNNER_TEMP`；否则直接调用 PATH 中的 `consilens-cli.sh`。
2. 以 `working-directory` 为基准执行 `verify`，参数由 inputs 映射；空值不会传空 flag。
3. 报告目录通过 `report-dir` output 暴露；存在 `verify-summary.md` 时自动写入 job summary。
4. `verify` 的非零退出码会让该 step 失败，从而实现 PR 阻断。

### JUnit / SARIF

- `junit`：`verify-junit.xml`，可被大多数 CI 直接解析为测试结果。
- `sarif`：`verify.sarif`，可配合 `github/codeql-action/upload-sarif` 上传到 GitHub Code Scanning。
- `markdown`：`verify-summary.md`，适合作为 job summary 或 PR 评论正文。

## 三、建议的门禁分层

| 场景 | 策略 |
| --- | --- |
| PR 冒烟 | `--fail-on any` + 小样本配置 |
| 每日全量 | `--fail-on new --baseline ...` + `--max-new-differences 0` |
| 迁移/割接 | `--fail-on any` + `--max-mismatch-rate 0` + `--required-columns` |
| 观察期 | `--fail-on none`，只上传报告 |

`verify` 每次都会重新执行比对，不复用历史 artifact；这样门禁结果只取决于当前数据与当前配置。
